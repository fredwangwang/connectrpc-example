# Connect RPC sample: Go server, Rust and curl clients

A small [Connect](https://connectrpc.com) example showing the same service over
HTTP/1.1, HTTP/2 and gRPC.

- **Server** (`server/`): Go, [connect-go](https://github.com/connectrpc/connect-go). One cleartext port serves
  HTTP/1.1 and HTTP/2 (h2c) and accepts the Connect, gRPC and gRPC-Web protocols.
- **Rust client** (`client-rs/`): [connect-rust](https://github.com/connectrpc/connect-rust) (`connectrpc` crate,
  pre-1.0). `--mode` selects `http1.1`, `http2` or `grpc`.
- **curl client** (`client-curl/`): a shell script that speaks Connect with JSON over HTTP/1.1 only.

## Service (`proto/sample/v1/sample.proto`)

| RPC | Shape | Purpose |
|---|---|---|
| `Echo` | unary | normal message |
| `ReportTelemetry` | unary, `repeated Event` | client-side batching, deduped by `batch_id` |
| `Subscribe` | server stream | notifications with heartbeats, resumable via `last_seen_id` |

Every response includes the HTTP version the server saw.

## Requirements

Go, Rust (MSRV 1.88 for `connectrpc`), `protoc`, `curl`, `xxd` (curl client streaming), and `buf` with the Go plugins.
`make tools` installs `buf`, `protoc-gen-go` and `protoc-gen-connect-go` into `~/go/bin`. Or skip all of that and use
`make build-docker`, which needs only Docker.

## Quick start

```sh
make tools          # once
make gen            # regenerate Go code from the proto (Rust is generated by build.rs)

make server         # terminal 1: listens on localhost:8080

# terminal 2
make client-rs   ARGS="--mode http2 --cmd subscribe --max 5"
make client-curl ARGS="--cmd telemetry --batch-size 3"
```

`make build` puts `server`, `client-rs` and `client-curl.sh` in `build/`.

### Build without a toolchain (Docker)

```sh
make build-docker   # same outputs in build/, needs only Docker (BuildKit)
```

The `Dockerfile` builds in a `rust` image with Go, `buf`, the Go plugins and `protoc` added, then exports just
the binaries to `build/`. Go and Rust versions are build args (`GO_VERSION`, `RUST_VERSION`). The server is
static; `client-rs` is dynamically linked against glibc (Debian bookworm), so it needs a glibc at least that
recent on the host. `buf` and the plugins are installed at `@latest`, so they are not version-pinned.

## Rust client

```
client-rs --mode <http1.1|http2|grpc> --cmd <echo|telemetry|subscribe> [flags]
```

| Flag | Default | |
|---|---|---|
| `--mode` | `http1.1` | `http1.1`: Connect over HTTP/1.1. `http2`: Connect over HTTP/2 (h2c, prior knowledge). `grpc`: gRPC over HTTP/2 |
| `--cmd` | `echo` | |
| `--addr` | `http://localhost:8080` | |
| `--message` | `hello` | echo message |
| `--batch-size` / `--batch-id` | `5` / `batch-1` | reuse a batch id to see server dedupe |
| `--last-seen-id` | `0` | subscribe resume point |
| `--max` | `8` | stop after N notifications (`0` = until the server ends the stream) |
| `-v`, `--verbose` | off | log headers and complete payloads to stderr |

gRPC needs HTTP/2, so there is no gRPC-over-1.1 mode.

## curl client

```
client-curl/client.sh [--cmd echo|telemetry|subscribe] [flags]
```

Same flags as the Rust client, minus `--mode` (always HTTP/1.1), with `-h/--help` and `-v/--verbose`.
Unary calls are plain JSON POSTs. `subscribe` uses `application/connect+json`: the script builds the 5-byte
envelope (flag byte + 4-byte big-endian length) for the request and parses envelopes from the response.

## Verbose output

`-v` on the Rust client wraps the transport, so it works the same for all three modes. It prints request and
response headers, trailers (`grpc-status`), and each body as hex plus the decoded message. Connect-streaming and
gRPC bodies are split into envelopes (`envelope flags=0x00 len=7: ...`), and gzip payloads are decompressed for
display.

It shows HTTP messages, not HTTP/2 frames (HEADERS, DATA, SETTINGS, HPACK); for those use the `h2` crate's trace
logging or `curl --http2-prior-knowledge -v`. The decoder knows only this sample's three methods and handles
gzip, not zstd.

`-v` on the curl client adds curl's own `-v` output (full HTTP/1.1 headers), the request body, and each streamed
envelope.

## Notes

- The server logs each request's HTTP version, path and `Content-Type`, which shows which protocol each client
  mode actually used (`application/proto`, `application/connect+proto`, `application/grpc+proto`).
- Telemetry dedupe state is in memory: it resets when the server restarts and never expires old batch ids.
- Streams end after a client-chosen `--max` or the server's 5-minute maximum lifetime.
- Client streaming and bidirectional streaming are not part of this sample.
